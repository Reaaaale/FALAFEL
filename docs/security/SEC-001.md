# SEC-001 — ESP32 cryptographic baseline assessment

Historical assessment of ESP-IDF 5.5.2. [SEC-002](SEC-002.md) subsequently
installed and validated isolated 5.5.6 for C6 development, with the ECC fix
present in compiled/linked code. Permanent-identity approval remains NO-GO.
The findings below describe the previous baseline and are retained as evidence.

Date: 2026-11-02. **Decision: NO-GO for permanent real identities on both
ESP32-C6 and ESP32-S3 with the current ESP-IDF 5.5.2 baseline.**

This is an assessment with limited test-harness corrections, not completion of
the ECC remediation. Source/provenance inspection is independent of functional
test results. No flash, real permanent identity, SDK installation or external SDK
modification was performed. Protocol, persisted formats, pairing, provider
implementation and `falafel_reconnect` were not changed.

## 2. Vulnerability applicability

| Finding | Classification for the inspected Falafel path |
|---|---|
| **CVE-2026-54435: ECC optimized modp side channel** | **Confirmed affected implementation and relevant call path.** Includes Curve25519 in all configurations. The installed reduction is unpatched. Falafel derives the public key from its long-term private key using the affected ECP path. Requires precise local/privileged execution traces; no remote key-extraction exploit was demonstrated. |
| CVE-2026-35336: `mbedtls_ecdh_calc_secret()` output overflow | Vulnerable library version, but **not applicable to this provider path**: it calls `mbedtls_ecdh_compute_shared()` and exports to an exactly validated 32-byte buffer with `mbedtls_mpi_write_binary_le()`. It never calls the affected API. |
| CVE-2026-54434: Everest all-zero X25519 secret | **Not applicable**: advisory affects Mbed TLS 4.1.0/TF-PSA 1.1.0, not this 3.6.5 legacy ECP path; Everest/PSA options are not selected for the provider. Merely building the Everest library is not selecting its API. |
| CVE-2026-50583: zero-length ECC PK parsing | **Not applicable to the inspected provider/configuration**: legacy built-in ECP, not driver-only PSA PK representation; raw peer keys must be 32 bytes, with no ASN.1/PK parser. Reassess if TLS/PK/PSA is integrated. |
| CVE-2026-25835: PSA RNG cloning | PSA-specific issue is **not reached by this provider**. Its legacy CTR-DRBG must nevertheless never be copied across fork/snapshot without reseeding. Runtime messaging does not fork. Crash-test forks are disposable fixtures, not proof of nonce uniqueness after cloning. |
| CVE-2025-66442: compiler-induced timing violations | **Not demonstrated applicable**: documented examples concern Clang select-optimize and padded RSA/CBC/ECB. C6 uses GCC and Falafel uses AES-GCM. This does not establish that all generated code is constant-time. |
| CVE-2026-34871: Linux entropy fallback | **Not applicable to ESP-IDF hardware polling**, or the macOS host. Do not confuse it with the separate ESP32 entropy-ownership finding below. |

No reviewed advisory establishes a direct HKDF-SHA256 or standalone AES-256-GCM
break in this provider path. This is not certification of every SDK feature:
TLS/X.509/RSA/DTLS/PSA subsystems need reassessment when actually enabled/used.

## 3. Provider and firmware call paths

`shared/crypto/falafel_crypto_mbedtls.c` implements X25519 key generation,
public derivation and shared secret, HKDF-SHA256, AES-256-GCM, SHA256, comparison,
zeroization and CTR-DRBG. It passes a DRBG callback for ECP randomization and
checks sizes. Blinding/randomization does not substitute for the official fix.

The relevant path is:

```text
falafel_async_encrypt/decrypt
  -> setup
  -> falafel_crypto_x25519_public_from_private
  -> mbedtls_ecp_keypair_calc_public
  -> software Curve25519 / old optimized modp
```

`setup()` repeats the derivation when processing envelopes, including before
their peer-header comparison completes. This supplies repeated operations on a
static scalar, but does not by itself turn the advisory into a demonstrated
remote timing attack. Disabling NIST optimization is not a Curve25519 workaround.

On C6 the effective hardware ECC configuration permits software fallback; the
Espressif accelerator hook handles NIST P-192/P-256, not X25519. The linked
experiment still contains `ecp_mod_p255`. Hardware ECC therefore does not bypass
the affected code. S3 has not been cross-built here; the same software X25519
source remains unsuitable under the same baseline. No claim of hardware
exploitability equivalence or S3 execution is made.

The firmware storage stub does not invoke crypto or provision identities. The
provider/core objects compile into its persistence component but are unused in
the final stub's X25519 call graph. The separate C6 crypto experiment does link
and exercise the provider; symbol inspection confirms the public-derivation
function, old reduction and entropy enable/disable in its ELF. A successful
storage firmware build is therefore not execution evidence for E2EE crypto.

The provider uses public Mbed TLS 3.6 APIs plus context fields through
`MBEDTLS_PRIVATE`. An upgrade to Mbed TLS 4.x is not a drop-in replacement;
prefer the corrected 3.6.x Espressif release over an unnecessary API migration.

## 4. RNG analysis

The actual chain is:

```text
falafel_crypto_init
  -> mbedtls_entropy_init
  -> mbedtls_ctr_drbg_seed(mbedtls_entropy_func, personalization)
  -> hardware entropy source
  -> mbedtls_hardware_poll
  -> esp_fill_random
```

The personalization string is domain separation, not entropy. Hardware poll
returns success and the requested length; it does not check whether the main
physical entropy source is enabled. Effective C6 configuration selects
`MBEDTLS_ENTROPY_HARDWARE_ALT` and `MBEDTLS_NO_PLATFORM_ENTROPY`. CTR-DRBG uses a
32-byte AES key, 48-byte initial entropy request and default reseed interval
10,000 random requests; prediction resistance is not enabled by the provider.
Automatic reseeding calls the same entropy function.

Espressif requires active RF or an enabled internal primary source. Bootloader
seeding/secondary oscillator noise alone is not a guarantee of continuous true
entropy after `app_main`. This condition is shared by C6 and S3. It is a
**confirmed missing integration precondition**, not evidence of measured key
predictability or an observed compromise.

The original standalone C6 experiment initialized crypto without RF/ADC entropy
ownership. SEC-001 now enables `bootloader_random_enable()` before seed, leaves
it enabled through the isolated crypto operations/reseeds, then disables it on
cleanup. The application starts no RF/ADC, so that ownership policy is specific
and documented. **It must not be copied blindly into a Wi-Fi/ADC application.**
The Noise-C feasibility experiment still directly calls `esp_fill_random` and
does not establish production entropy ownership; it is isolated from the Mbed
TLS provider and not approved for permanent identities.

For the final application, define ownership/lifetime across startup, RF on/off,
ADC use, sleep/wake and every reseed. Neither seeding only once while RF is on
nor statistical tests of output establish that future reseeds are safe.

Noise K uses nonce zero with a newly derived key per envelope; that is not an
intrinsic GCM nonce-reuse bug. It depends on fresh ephemeral randomness. Repeated
ephemerals can repeat key/nonce; history's random 96-bit nonces likewise depend
on correct entropy/DRBG state across reboots. No protocol change is needed to
correct entropy ownership.

## 5. Least-invasive correction and changes actually made

Recommended: migrate the **complete official SDK** to ESP-IDF v5.5.6 with its
pinned Mbed TLS 3.6.7 and supported tools, then validate both target builds and
hardware entropy lifecycle. The fixed submodule provenance is confirmed, but
that full environment has not been built/tested here. Its recommended C6 tools
differ from the installed ones. No SDK or toolchain installation was performed.

An unvalidated replacement of only the SDK submodule would mix Espressif port
code/tool assumptions. A manual backport involves several ECC source/header
changes and dependencies; it is not the preferred alternative while an official
release exists. No speculative ECC patch or library swap was applied. No
alternative cryptographic library is necessary. SDK migration remains pending,
so the confirmed CVE remains unresolved in the current build.

Implemented only:

- Explicit internal entropy lifecycle and test-only warning in
  `experiments/esp32c6-crypto/main/main.c`; declared `bootloader_support` dependency
  is an existing ESP-IDF component, not a new external library.
- Embedded RFC public-derivation and low-order-input checks for future runs.
- Host tests rejecting five low-order/non-canonical peer inputs, checking output
  clearing and rejecting a short shared-secret buffer without overwriting it.
- Public provider contract documents entropy availability at seed/reseed and
  prohibits cloning a live DRBG without reseeding. Provider behavior unchanged.

Compiler-macro evidence was extracted from the actual provider translation unit
using `compile_commands.json`, not inferred solely from Kconfig. Generated
evidence: `build/sec001-c6-config.json`. Host tests used published vectors and
disposable identities/temporary fixtures only; no real permanent identity.
Source hashes verified provider implementation, pairing, envelopes and reconnect
implementation/header unchanged during the session. The separate reconnect test
file changed concurrently outside this work and was left untouched; the reported
16-test root suites do not include it. No functional test measures a side channel,
proves entropy quality, certifies physical key protection or clears a CVE.

## 7. Residual risks and closure gates

1. Current compiled ECC remains vulnerable; repeat source/config/object provenance
   checks after official SDK migration, not just a version-string comparison.
2. Validate RNG ownership on both chips during initial seed/reseed and power-state
   transitions; execute the revised disposable C6 experiment before using it as
   hardware evidence. No real keys are needed for these tests.
3. Repeat RFC and negative tests on the actual corrected C6/S3 backend, including
   GCM decrypt/tag/AAD failure and output clearing; current new tests are host
   executed or embedded compiled only.
4. Protected identity enrollment/storage/backup/rotation is not integrated into
   firmware. Secure Boot and flash encryption are disabled in inspected builds.
   The history backend does not store/protect private identities. Define the
   physical-access threat model and verify key protection before permanent use.
5. Existing Noise K offline design lacks retrospective confidentiality after
   recipient static-private-key compromise. Retention/rollback and relay access
   security are separate limits; no protocol change is made by SEC-001.

**NO-GO remains for permanent identities on C6 and S3.** The assessed experiment
may be used with disposable data; SDK fix validation, entropy integration and
identity protection remain open. SEC-001 analysis is complete; remediation is
partial, not security approval.
