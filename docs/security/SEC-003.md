# SEC-003 — ESP32-C6 hardware crypto experiment

Prepared: 2026-11-02. Revalidated: 2026-11-03. **Software preparation: verified/ready. Hardware validation:
NOT RUN. SEC-003 remains OPEN pending physical tests and review. Permanent real
identities: NO-GO on C6/S3.** No flash, serial monitor, eFuse operation, security

## Objective and reuse

The existing ESP-IDF project `experiments/esp32c6-crypto/` is retained; there is
no second ESP-IDF application. It compiles Falafel's actual
`shared/crypto/falafel_crypto_mbedtls.c`. Production source/API, protocol, pairing,
storage formats, EMB-001/002 and their tests are not modified.

The original experiment checked provider initialization, HKDF RFC5869, a
one-block AES-256-GCM encryption vector, RFC7748/public derivation, low-order
inputs and temporary ECDH. It lacked GCM decryption/tampering, direct provider RNG
exercise, observed automatic reseed, injected failures, comprehensive cleanup,
per-case logs and a repeatable reboot/capture procedure. Historical C6 runs from
earlier SDKs do not validate this new image or entropy policy.

The native mode of the same project rehearses portable test logic and runs the
existing host provider regression against the SEC-002 SDK's Mbed TLS source.
Native entropy is the host OS, never ESP32 hardware evidence.

## RNG path and ownership

The inspected 5.5.6 code follows:

Source anchors below are relative to the pinned SDK; the Falafel provider is
`shared/crypto/falafel_crypto_mbedtls.c` in this repository:

- `components/mbedtls/port/esp_hardware.c`: `mbedtls_hardware_poll`.
- `components/mbedtls/mbedtls/library/entropy.c`: strong-source registration
  and entropy accumulation.
- `components/mbedtls/mbedtls/library/ctr_drbg.c`: seed, generation and reseed.
- `components/esp_hw_support/hw_random.c`: `esp_fill_random` / `esp_random`.
- `components/bootloader_support/src/bootloader_random_esp32c6.c`: C6 SAR
  enable/disable sequence.
- `build/sec003-20261103/crypto-c6-ready/sdkconfig`, `compile_commands.json` and linked
  ELF/disassembly: effective configuration and compiled routing evidence.

```text
Falafel init / automatic random reseed
 -> experiment-only entropy callback proxy
 -> real mbedtls_entropy_func / entropy accumulator
 -> mbedtls_hardware_poll (counting wrapper -> original SDK function)
 -> esp_fill_random -> esp_random -> hardware RNG register
```

`MBEDTLS_ENTROPY_HARDWARE_ALT` and `MBEDTLS_NO_PLATFORM_ENTROPY` select hardware
polling on C6. Entropy initialization registers that callback as a strong source
with a 32-byte threshold. The port calls `esp_fill_random`, returns the requested
length and success; this does **not** assess physical entropy health.

The provider seeds CTR-DRBG with the real Mbed accumulator and its domain string,
not a fixed seed. Effective parameters are a 32-byte AES key, 48-byte initial
entropy request and default reseed interval 10,000. The pinned implementation
checks `reseed_counter >= reseed_interval` before generating output. The suite
requests enough provider output to observe a new entropy callback and hardware
poll, without changing the interval or inspecting private provider layout.

On C6, `hw_random.c` also initializes the independent RNG clock through
`ESP_SYSTEM_INIT_FN(init_rng, SECONDARY, BIT(0), 102)`. `esp_random()` mixes
register reads with the asynchronous LP timer and enforces a sampling delay
(C6 `APB_CYCLE_WAIT_NUM = 160 * 16`); enabling its clock and mixing timer values
do not establish sufficient entropy. The bootloader calls enable during
initialization and disable in `bootloader_utility.c` before application handoff.

RF must be active, or the internal SAR primary source enabled. Merely compiling
Wi-Fi, initializing its structures, or relying on bootloader/secondary oscillator
noise is insufficient. RF power saving can remove its entropy source. ADC users
and RF startup must not conflict with `bootloader_random_enable()` ownership.
After light sleep, source availability must be re-established before the next
entropy poll/reseed; retained DRBG state is not proof of current entropy. Deep
sleep restarts require the startup/seed policy again. Neither mode is exercised
here, and cold power-cycle tests do not validate sleep/wake integration.

This isolated app starts no RF, user ADC, TLS, sleep or networking. After the
10-second capture grace period it enables the SDK's internal SAR source before
provider initialization, retains exclusive ownership through all seeds/reseeds,
frees/wipes provider state and disables SAR before finishing. The C6 SDK enables
ADC clocks, internal reserved-channel patterns and triggering; disable stops that
path. These are reversible peripheral operations, not eFuse programming. The
void control API and counters cannot certify that the analog source is healthy.

### Diagnostic interposition, not a production change

Only this experiment's provider object has a compile-time alias from
`mbedtls_entropy_func` to `sec003_entropy_func`. Positive calls forward unchanged
to the real accumulator. Two deliberate callback errors test failed initialization
and failed automatic reseed/recovery. They do not simulate or detect low physical
entropy. The production provider file is unchanged; a separate unaliased host
regression target checks its original behavior.

On ESP32 only, GNU `--wrap=mbedtls_hardware_poll` counts original hardware polls
and returned byte counts. It does not inspect/replace positive output. Linked
disassembly confirms both the proxy and original callback paths. Instrumentation
assumes this single-owner diagnostic app, not a concurrent production telemetry
facility. It must not be copied blindly into Wi-Fi/ADC/power-management firmware.

| Evidence class | What it can establish |
|---|---|
| Static/config/link inspection | Correct SDK/provider/source, callback routing, control order, enabled primitives, reseed rule, no persistent key I/O or RF/sleep initialization |
| Physical execution | This board completes initialization, vectors, ephemeral exchanges, tamper/error rejection, cleanup/resource checks, actual callback activity and repeated boot observations |
| Not established by simple statistics | Entropy quantity/unpredictability, analog health, resistance to manipulation/side channels, permanent-key protection, secure RF/ADC/sleep transitions |

Nonzero/different RNG blocks and distinct public fingerprints only catch gross
failures. They are not an entropy estimate. Production entropy ownership across
all power states remains unverified even after functional hardware PASS.

## Test matrix and log contract

| Case | Check |
|---|---|
| `init_failure` | Injected callback failure -> RANDOM_FAILED; failed context cleared |
| `init` | Real provider initialization and observed hardware poll on ESP |
| `rng_sanity` | 32 provider-generated blocks; gross zero/repeat check only |
| `automatic_reseed` | Reach default threshold and observe real callback/hardware activity |
| `reseed_failure_recovery` | Injected reseed error propagated, then real retry succeeds |
| `hkdf_kat` | RFC5869 SHA256 known-answer vector |
| `gcm_kat` | Published AES-256-GCM one-block ciphertext/tag and decrypt |
| `x25519_rfc` | RFC7748 shared secret/public derivation; five low-order encodings rejected and output cleared |
| `x25519_ephemeral` | Two temporary key pairs, derived public keys, matching nonzero ECDH; HKDF-derived disposable AES key |
| `gcm_roundtrip` | 117-byte non-block-aligned payload, AAD and fresh nonce roundtrip |
| `gcm_tamper` | Altered tag, ciphertext and AAD rejected; returned plaintext buffer zeroed |
| `invalid_arguments` | Null/uninitialized context paths, lengths/capacity guards and oversized RNG request rejected |
| `cleanup_reinit` | Context erased, freed context rejected, three init/random/free cycles |
| `platform_resources` | Heap integrity, at least 512 bytes minimum free task stack, suite-owned context/scratch erased |

The suite clears owned scratch/private/shared/key buffers on success and failure;
private/DH values are cleared promptly after derivation. Verification concerns
accessible owned objects, not CPU registers, caches, DMA or every unreachable
internal library allocation. All identities are disposable RAM-only tests. No
NVS, RTC identity, seed persistence or provisioning is added.

No RNG samples, private keys, DH secrets or derived AES keys are logged. The only
crypto-derived boot label is SHA256 of two **public** temporary keys. Repetition
across runs is a failure to investigate; uniqueness does not prove entropy.
Logs also contain the public ELF hash, reset reason, case labels, counters and
heap/stack/timing metadata.

### Reboot protocol

1. Record board revision, USB-UART port, supply method, binary/ELF hashes and date.
   Do not edit/rebuild between runs. Collect five Reset-button runs, waiting for
   the full RESULT/STATUS before each next reset.
2. Collect five genuine cold runs: remove **all** USB/external power for at least
   10 seconds, then reconnect only the USB-UART cable. Keep monitor reconnecting,
   or restart it with `--no-reset` promptly. Update the port if enumeration changes.
   The 10-second app delay permits attachment. Do not press Reset during a cold
   capture; that would change the documented physical procedure.
3. Keep operator notes identifying warm/cold runs. Reset reason alone cannot
   prove a power removal or distinguish every EN reset from cold power-on.
4. Partial capture, missing BEGIN or reset mid-test is not a PASS. Preserve that
   log separately, start a fresh capture file and repeat the affected run. Appended
   logs must all refer to one ELF; never mix builds or count a duplicated capture.

## PASS/FAIL and remaining security gates

Per-run functional PASS requires all 14 cases, RESULT PASS/14/0/cleanup=1,
positive hardware polling, exactly two injected failures, stack margin >=512,
heap integrity and completion within 120 seconds after BEGIN. Any failed case,
panic/watchdog/brownout, unexpected reboot, missing result, wrong ELF or repeated
public fingerprint is FAIL/inconclusive and requires investigation, not automatic
store regeneration or a security bypass. Do not enable dumps to diagnose with
real secrets; this experiment uses disposable data only.

Software readiness is approved separately. A functional hardware experiment
GO requires actual reviewed logs from this board plus the five warm/five cold
operator record. **No such record exists from this preparation: SEC-003 is OPEN.**
Even that GO does not approve permanent identities: RF/ADC/sleep integration,
physical entropy assurance, S3 tests, protected identity provisioning/storage,
backup/rotation and physical-access threat model remain separate gates.
