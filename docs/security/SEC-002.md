# SEC-002 — Isolated ESP-IDF 5.5.6 baseline validation

Date: 2026-11-02.

**GO for adopting the isolated 5.5.6 environment as the C6 development baseline.**
**NO-GO for permanent real identities on C6/S3:** device entropy lifecycle and
key protection remain unverified. No flash or hardware execution was performed.
This is software baseline validation, not full-device security certification.

## Preliminary verification and isolation

SEC-001 was read in full before installation. The official v5.5.6 release and
its Mbed TLS pin were checked against Espressif's GitHub release/API and the
upstream advisory. The installed corrective source was then checked again.

## Evidence for CVE-2026-54435 correction

Evidence is stronger than a version-string or functional PASS:

1. The official release pins Mbed TLS commit `2b96dd8e...`; the installed clean
   SDK/submodule are exactly those commits, with no manual cryptographic patch.
2. In the new submodule's official Git history, both advisory endpoints are
   ancestors: basic fix `6b4b14ae719c4f46ea70600d63b0d50dc727ff3a` and additional
   improvements `05ce3e90eb863b751c4464633a94239fd1938608`.
3. Installed `library/ecp_curves.c` is the reviewed corrected source, SHA256
   `db2d2c08fd5b7a28d9a082cdce1af6c266bafd5dfbdee0f162183a07fa0bfe86`.
4. Both fresh embedded compilation databases select that source from the new
   SDK. Preprocessing the actual provider translation units gives Mbed TLS
   `0x03060700`, not headers from the old installation.
5. The crypto experiment ELF includes public derivation, ECP public calculation
   and `mbedtls_ecp_mod_p255_raw`. Disassembly of `ecp_mod_p255` shows its call
   into that corrected raw reduction (address 0x42015880 in this build).

The path remains Falafel public-from-private -> `mbedtls_ecp_keypair_calc_public`
-> software X25519, now with corrected reduction. C6's hardware ECC NIST support
does not replace X25519. No protocol, pairing, persistent encoding, primitive or
provider implementation was changed. No alternative crypto library was added.

Reproduce provenance/configuration/link checks after the builds/tests with:

```sh
bash tools/with-idf-5.5.6.sh python tools/verify-sec002.py > build/sec002/evidence.json
```

The verifier checks the installed pins, clean source, advisory ancestry, source
hash, actual compiler/header paths, linked reduction call and completed test logs.
It is specific to these build directories, not a general vulnerability scanner
or permanent-key approval mechanism.

## Configuration and compatibility

Both embedded targets were configured from their existing defaults into fresh
SDKCONFIG paths. Existing `firmware/sdkconfig` and experiment configuration were
preserved. No compatibility edit was required in application source or CMake.
The provider's 1,536-byte context bound still compiles successfully.

Effective selection: legacy ECP/ECDH with Curve25519, hardware-ECC software
fallback, AES/GCM hardware alternatives, HKDF, SHA and CTR-DRBG. Neither the PSA
nor Everest path is selected by the provider. API/field access remains compatible
with the Mbed TLS 3.6 family; this is not a migration to Mbed TLS 4.x.

Entropy selection remains `MBEDTLS_ENTROPY_HARDWARE_ALT`, with no platform-OS
entropy source. CTR-DRBG still has a 32-byte key, 48-byte entropy request and
10,000-request default reseed interval. **Updating the library has not established
entropy availability at startup/reseed, RF/ADC transitions or sleep/wake.**
The isolated experiment's SEC-001 source ownership remains unchanged and has
only been built. Secure Boot and flash encryption remain disabled in the tested
development configurations. There is still no production identity store.

The firmware remains the storage-probe stub; its successful build does not mean
embedded E2EE execution. The separate crypto experiment does link the provider.
S3 compilation and physical device tests were not performed or approved here.

## Builds and tests actually executed

All five build directories were initially empty; no old firmware/host objects
or generated SDKCONFIG files were reused. Host builds override FetchContent to
the **Espressif Mbed TLS source inside the candidate SDK**, rather than reusing
the previous upstream archive. Host native defaults do not execute ESP hardware
AES/GCM or its hardware RNG; they exercise the portable provider/core.

| Clean C6 crypto experiment | PASS, `falafel_esp32c6_crypto.bin` 0x3b810 / 243,728 bytes |

Host coverage includes RFC X25519/public derivation, low-order peer rejection,
short buffers, HKDF, GCM/tag failure, provider fault injection, mailbox crash
recovery and real local E2EE/TCP relay processes. Simulator tests include 100
messages per direction, restart/read/delivery restoration and 41 history crash
boundaries. ASan/UBSan flags apply to Falafel **and the candidate vendor Mbed TLS
sources**, verified in the compilation database.

No crypto or embedded compiler warnings were found. The simulator linker emits
the existing duplicate-LVGL-library warning; it is unrelated to the crypto SDK
and all four tests pass. No application compatibility regression was observed
within the executed coverage. Test identities are disposable fixtures only.

EMB-002 was excluded: its connection/reconnect code and tests were not edited
or added to these builds. Concurrent changes to `falafel_connection.c/.h` were
observed and left untouched. Provider, pairing, mailbox/history sources,
reconnect implementation/test and existing SDKCONFIG fingerprints were preserved
by this work. Passing these suites is not EMB-002 acceptance.

## Decisions and remaining work

**Development baseline: GO for C6.** Adopt the isolated official 5.5.6 SDK,
supported compiler and matching Mbed TLS as a unit. Source and linked-code
evidence show the specific SEC-001 ECC correction is present. This does not
certify every SDK feature or establish S3/hardware validation.

**Permanent real identities: NO-GO for C6 and S3.** Next steps remain:

1. Authorized disposable-data execution on C6, then S3 builds and hardware tests.
2. Verify primary entropy ownership at initial seed/reseed and RF/ADC/power-state
   transitions; statistical output tests alone cannot establish this property.
3. Define and verify protected identity provisioning/storage/backup/rotation and
   the physical-access threat model, including boot/flash protection decisions.
4. Repeat storage power-cut, GC/capacity and integrated worker/network tests.

No flash, commits, pushes or destructive operations were performed. SEC-001
remains the historical record for 5.5.2; its old-baseline NO-GO is not erased.

available locally at its pinned version; no simulator source was changed):

```sh
ctest --test-dir build/sec002/simulator --output-on-failure
```
